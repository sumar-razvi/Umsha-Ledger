## Non-negotiable accounting invariants

These must be enforced in `core/validate.js` and covered by tests. If any code path can break one, it is a bug.

1. **Every journal entry balances**: sum of debits equals sum of credits, to the paisa.
2. **Money is integer minor units (paisa)**. Never store or add floats. Convert at the UI edge only. `Rs 1,250.50` is stored as `125050`.
3. **Posted entries are immutable.** Corrections are made by a reversing entry plus a new entry. No UPDATE or DELETE on `Journal` or `JournalLines` ever.
4. **Documents post, people don't.** Invoices, bills, payments, stock moves generate journal entries through `core/posting.js`. Manual journals exist only for Finance/Owner roles.
5. **Every journal line carries a `brand` segment**: `UMSHA` (made-to-order), `MIRAE` (ready-to-wear), or `SHARED`. This is what makes the multi-brand P&L work. No line may have an empty brand.
6. **Locked periods reject postings.** Any entry dated in a closed period fails.
7. **Control accounts reconcile to sub-ledgers.** AR control = sum of open customer balances; AP control = sum of open vendor balances; inventory accounts = stock valuation report.
8. **Idempotency.** Every write request has a client-generated `requestId`. A repeated `requestId` returns the original result without posting twice (Karachi mobile networks retry).
9. **One writer at a time.** All writes run inside `LockService.getScriptLock()`.
10. **Every write is audit-logged** with user email, timestamp, action, and document ID.

## Domain vocabulary (use these terms in code and UI)

| Term | Meaning |
|---|---|
| MTO | Made-to-order. UMSHA couture, bridal, formals. Each order is a **Job** with its own costing. |
| RTW | Ready-to-wear. Mirae. Stocked **SKUs** sold at the Mirae Karachi store, online, exhibitions. |
| Job | A cost-collection bucket. `MTO_ORDER` (one client garment/outfit set) or `RTW_BATCH` (production run of SKUs). |
| Karigar | Artisan (embroidery, stitching, adda work). Paid per piece/job. Treated as a vendor. |
| Advance | Customer deposit on an MTO order before delivery. A liability, not revenue. |
| Brand segment | `UMSHA` / `MIRAE` / `SHARED` tag on every journal line. |
| Paisa | 1/100 of a rupee. Storage unit for all amounts. |

Do not conflate UMSHA MTO workflows with Mirae RTW store workflows. They share a ledger but have different documents and screens.

## Coding conventions

- Plain ES2020. No transpiler. Apps Script V8 runtime supports it.
- `/core` files: each exports pure functions via `if (typeof module !== 'undefined') module.exports = {...}` so the build script can strip it.
- `/core` files import siblings only as `const Money = require('./money.js');` (variable = file name in PascalCase). The build wraps each file in a namespace of that name in `Core.gs` (`Money.parseRupees(...)` works in both Node and Apps Script) and fails on any other import style. `npm test` fails if `Core.gs` is stale, so run `npm run build` after changing `/core`.
- IDs: human-readable, prefixed, year-scoped, zero-padded: `INV-2026-00042`, `BILL-2026-00007`, `JOB-2026-00113`, `JE-2026-00981`. Generated server-side from the `Sequences` tab under lock.
- Dates: ISO `YYYY-MM-DD` strings in storage. Timezone `Asia/Karachi` for all server date logic.
- Sheets I/O: read whole ranges with `getValues()` once, never cell-by-cell in loops. Write with `setValues()` in batches. Append via `getRange(lastRow+1, 1, n, cols).setValues()`.
- Front-end to Apps Script calls: `fetch(API_URL, {method:'POST', headers:{'Content-Type':'text/plain;charset=utf-8'}, body: JSON.stringify(req)})`. The `text/plain` content type avoids a CORS preflight, which Apps Script cannot answer. Do not "fix" this to `application/json`.
- Currency display: `Rs 1,25,000` style is NOT required; use `Rs 125,000` (standard grouping). Configurable in Settings.
- UI copy: plain English, short. Staff at the store may be non-accountants: say "Money received" not "Debit cash".
- Errors: server returns `{ok:false, code, message}`; never throw raw stack traces to the client.

## How to work

- Before coding a milestone, restate its acceptance criteria from `docs/07-build-plan.md` and list the test scenarios from `docs/08-test-scenarios.md` it must pass.
- Write the `/core` logic and its tests first. Then the Apps Script I/O. Then the UI.
- Run `node --test` before declaring anything done. All scenarios for completed milestones must stay green.
- If a requirement is ambiguous, check `docs/09-open-decisions.md`. If it isn't there, add it there with your proposed default and continue with that default.
- Keep `docs/` updated when you change a schema or posting rule. The docs are the source of truth, the code follows.
- Never commit secrets. The Apps Script URL and the Google OAuth client ID go in a `CONFIG` block at the top of `index.html`; the Sheet ID lives in Apps Script Script Properties.
